## 3.1 첫 방법: 픽셀마다 외적 (`31f3aa5`, 2025-07-20)

삼각형을 채우는 가장 단순한 방법은 이렇습니다.

1. 세 꼭짓점을 감싸는 **경계 상자**(bounding box)를 구한다.
2. 상자 안의 픽셀마다 "삼각형 안인가?"를 묻는다.
3. 안이면 칠한다.

"안인가?"를 묻는 도구가 **무게중심 좌표**(barycentric coordinates)입니다. 삼각형 안의 점 P는 세 꼭짓점의 가중 평균 `P = w·A + u·B + v·C` (단, `w + u + v = 1`)로 쓸 수 있고, 세 가중치가 모두 0 이상이면 P는 삼각형 안에 있습니다. 첫 코드는 이 세 값을 **외적 한 번**으로 구했습니다.

```cpp
// 31f3aa5 Renderer.cpp (요약)
SRMath::vec3 u_vec = SRMath::cross({ pv2.x - pv0.x, pv1.x - pv0.x, pv0.x - p.x },
                                   { pv2.y - pv0.y, pv1.y - pv0.y, pv0.y - p.y });
if (std::abs(u_vec.z) < 1) continue;     // 넓이가 0에 가까운 삼각형은 건너뜀
float u = u_vec.x / u_vec.z;
float v = u_vec.y / u_vec.z;
float w = 1.0f - u - v;
if (w >= 0 && u >= 0 && v >= 0)
    DrawPixel(x, y, color);
```

이 코드는 정확하지만 픽셀마다 외적(곱셈 6번), 나눗셈 2번을 합니다. 그리고 같은 커밋에는 이런 코드가 함께 있었습니다.

```cpp
// 31f3aa5: 삼각형 하나를 그릴 때마다
const unsigned int numThreads = std::thread::hardware_concurrency();
std::vector<std::thread> threads;
for (unsigned int i = 0; i < numThreads; ++i)
    threads.emplace_back([...]() {
        for (int y = minY + i; y <= maxY; y += numThreads)   // 행을 번갈아 나눠 맡음
            ...
    });
for (auto& t : threads) t.join();
```

<div class="note fail"><span class="label">무엇이 문제였나</span>
<b>삼각형 하나마다</b> CPU 코어 수만큼 스레드를 만들고 끝나기를 기다립니다. 운영체제 스레드 하나를 만들고 정리하는 데는 보통 수십 마이크로초가 걸리는데, 화면에서 몇 픽셀밖에 안 되는 작은 삼각형을 칠하는 일은 그보다 훨씬 짧습니다. 모델 하나에 삼각형이 수천~수만 개이므로 시간 대부분이 스레드를 만들고 기다리는 데 쓰입니다. 병렬화 자체는 맞는 방향이었지만 <b>나누는 단위</b>가 너무 작았습니다. 올바른 단위(화면 타일)는 10장에서 다룹니다.</div>

## 3.2 두 번째 방법: edge function을 더하기만 (`5751375`, 2025-07-28)

8일 뒤 코드는 완전히 바뀌었습니다. 외적을 픽셀마다 새로 계산하지 않고, 2장의 Bresenham처럼 **한 칸 갈 때 일정한 값만 더합니다.**

변 AB에 대한 **edge function** `E(x, y) = (B.y − A.y)·(x − A.x) − (B.x − A.x)·(y − A.y)`는 점이 변의 어느 쪽에 있는지를 부호로 알려 줍니다. 세 변 모두에서 같은 쪽(0 이상)이면 삼각형 안입니다. 그리고 E는 x에 대한 1차식이라서 x가 1 늘면 정확히 `B.y − A.y`만큼 변합니다.

```cpp
// 5751375 Renderer.cpp
const int dx01 = p0.x - p1.x,  dy01 = p0.y - p1.y;
const int dx12 = p1.x - p2.x,  dy12 = p1.y - p2.y;
const int dx20 = p2.x - p0.x,  dy20 = p2.y - p0.y;

// 경계 상자의 시작점(minX, minY)에서만 곱셈으로 계산
int w0_row = dy12 * (minX - p1.x) - dx12 * (minY - p1.y);
int w1_row = dy20 * (minX - p2.x) - dx20 * (minY - p2.y);
int w2_row = dy01 * (minX - p0.x) - dx01 * (minY - p0.y);

for (int y = minY; y <= maxY; ++y) {
    int w0 = w0_row, w1 = w1_row, w2 = w2_row;
    for (int x = minX; x <= maxX; ++x) {
        if (w0 >= 0 && w1 >= 0 && w2 >= 0) { /* 칠하기 */ }
        w0 += dy12;  w1 += dy20;  w2 += dy01;       // 오른쪽으로 한 칸: 덧셈 3번
    }
    w0_row -= dx12;  w1_row -= dx20;  w2_row -= dx01;   // 아래로 한 줄: 뺄셈 3번
}
```

세 값 `w0, w1, w2`는 그 자체로 무게중심 좌표의 분자입니다. 셋을 합으로 나누면 3.1의 `w, u, v`와 같아집니다. 그래서 "안인가?"는 덧셈 3번과 비교 3번이 되고, 나눗셈은 안쪽 픽셀에서만 합니다.

## 3.3 숨어 있던 정밀도 문제

`5751375`의 변수는 모두 `int`였습니다. 화면 좌표 `p0.x` 같은 실수가 정수로 잘리면서 **소수점 아래 위치가 사라집니다.** 그 결과는 데모의 "첫 코드 (정수 좌표)" 모드에서 볼 수 있습니다.

- 꼭짓점이 한 픽셀 안에서 움직여도 삼각형 모양이 변하지 않다가, 경계를 넘는 순간 한 칸씩 **뚝뚝 끊겨** 움직입니다. 물체가 천천히 움직일 때 가장자리가 떨리는 원인입니다.
- 판정 위치가 픽셀 중심이 아니라 **픽셀 왼쪽 위 모서리**입니다. 그래서 같은 삼각형이 반 픽셀씩 어긋나 보입니다.

## 3.4 그 뒤에 어떻게 바뀌었나

지금의 `Rasterizer::DrawTriangleImpl`은 같은 edge function 구조를 유지하면서 네 가지가 바뀌었습니다.

### (1) 1/256 픽셀 고정소수점 + 픽셀 중심

```cpp
// src/Renderer/Rasterizer.cpp (현재)
bool toFixed(float input, std::int64_t &result)
{
    const float scaled = input * 256.f;          // 1/256 픽셀 단위 정수
    if (!(std::abs(scaled) < 0x1p60f))           // NaN, inf, 너무 큰 값은 거부
        return false;
    result = static_cast<std::int64_t>(scaled);
    return true;
}
...
// 시작점은 픽셀 중심 (x + 0.5, y + 0.5)에서 계산
toFixed(t.dy12 * (x0 + 0.5f - p1.x) - t.dx12 * (y0 + 0.5f - p1.y), r0)
```

정수로 더하기만 하는 장점은 유지하면서, 위치는 1/256 픽셀 단위로 기억합니다. 실수로 계속 더하면 오차가 쌓이지만 정수 덧셈은 오차가 없어서, 같은 삼각형은 어느 스레드가 어느 타일에서 그려도 정확히 같은 픽셀을 칠합니다. 변수가 `int64`인 이유는 큰 화면에서 `int32`가 넘칠 수 있기 때문이고, 넘칠 가능성이 있는 삼각형은 미리 검사해서 버립니다(`safeEdge`).

### (2) 4픽셀씩 건너뛰기

경계 상자의 왼쪽 빈 부분을 한 칸씩 검사하는 대신, 4픽셀 묶음 전체가 확실히 바깥이면 한 번에 건너뜁니다.

```cpp
// 1. Skip leading blocks of 4 pixels that are guaranteed outside
while (x + 3 <= x1)
{
    if (((w0 + maxOffset0) | (w1 + maxOffset1) | (w2 + maxOffset2)) < 0)
    { w0 += dy12_4; w1 += dy20_4; w2 += dy01_4; x += 4; }
    else break;
}
```

`(a | b | c) < 0` 은 "셋 중 하나라도 음수인가?"를 비교 한 번으로 묻는 방법입니다. 2의 보수에서 음수는 맨 위 비트가 1이므로, 셋을 OR한 값의 맨 위 비트는 하나라도 음수일 때 1이 됩니다. 비교 3번과 분기 3번이 OR 2번, 비교 1번, 분기 1번이 됩니다. 이런 최적화는 소스가 아니라 생성된 어셈블리를 보고 찾습니다(13장).

### (3) 안쪽 판정 경계: 같은 변을 두 삼각형이 공유할 때

판정은 `>= 0`이라서 두 삼각형이 공유하는 변 위의 픽셀은 **양쪽 모두** 칠합니다. 많은 렌더러는 이를 "top-left 규칙"으로 한쪽에만 주지만, 이 렌더러는 다른 방법을 택했습니다. 깊이가 같으면 **삼각형 번호(primitive ID)가 작은 쪽이 이깁니다.** 그래서 그리는 순서나 스레드와 상관없이 결과가 항상 같습니다. 데모의 "옆 삼각형 보기"를 켜면 두 번 칠해지는 픽셀이 표시됩니다.

### (4) 아예 칠할 픽셀이 없는 삼각형은 미리 버리기 (PR #56)

군집 장면(삼각형 188만 개)에서 대부분의 삼각형은 화면에서 1픽셀보다 작았습니다. 픽셀 중심을 하나도 덮지 않는 삼각형은 래스터 단계까지 보낼 필요가 없습니다. `CoversNoPixel`은 경계 상자가 4×4 이하인 삼각형에 대해 **래스터 루프와 같은 식, 같은 순서**로 미리 검사합니다. 준비되는 삼각형이 134만 개에서 30만 개로 줄었고 fill이 **66.0%** 빨라졌으며, 결과 픽셀은 한 개도 바뀌지 않았습니다. 이 이야기는 27장에서 자세히 다룹니다.

<div class="note fail"><span class="label">시도했지만 버린 것: 커버리지 비트마스크</span>
경계 상자의 각 행을 SSE로 한 번에 판정해 "칠할 픽셀" 비트마스크를 만드는 방식도 시도했습니다. 조사해 보니 경계 상자 행의 68%가 비어 있었고, 왼쪽 빈칸 건너뛰기 단계가 실제로 칠하는 픽셀보다 3.4배 많았습니다. VTune에서 래스터 CPU 시간은 17.7초 → 14.5초(−18%)로 줄었지만 <b>프레임 시간은 0.5~1.7%밖에 줄지 않아</b> 채택 기준(2%)에 못 미쳤습니다. 24스레드가 일을 나눠 하면 한 단계의 CPU 절감이 벽시계 시간에 거의 반영되지 않는다는 교훈은 21장에서 다룹니다.</div>
